# 福委會 — 規格正本

> owner 2026-08-21 的原話：
>
> 「我有幾個福利池，一個是**快樂**、一個是**進修**，這兩塊員工都可以登記，
> 他們登記後**我審核通過，就進公司請款**。我**每年會撥一筆錢**進這個池。」
> 「這個池子的名稱是**福委會**。」
>
> 這份文件就是照那三句話寫的。跟現況不符就改這份，程式跟著這份走。

## 0. 一句話

```
每年撥款 ──▶ 池（快樂 / 進修）
              ▲
員工登記 ──▶ 待審 ──owner 核准──▶ 已核准（進公司請款）──▶ 已付款
              └──退回──▶ 退回（本人可改可刪，改完自動重新送審）
```

**餘額 ＝ Σ撥款 − Σ(已核准 ＋ 已付款)**

## 1. 三張表

| 表 | 是什麼 | 關鍵欄 |
|---|---|---|
| `hr_benefit_pools` | 池（快樂／進修）。**跨年度滾動** | name / status(open,closed) / entity |
| `hr_benefit_fundings` | 每年公司放進池裡的那筆錢 | year / amount / fund_date |
| `hr_benefit_entries` | 員工登記的一筆花費 | title(自由文字) / amount / staff_id / status |

**為什麼撥款自己一張表**，不跟登記混成一本帶號流水帳（Notion 原本是那樣）：
撥款沒有請款人、不需要審核、也不該進公司請款 —— 跟員工登記是兩種東西。
混在一起的話，員工登記時把金額填成正數就變成一筆「撥款」，池憑空多錢。

**項目是自由文字**（電影名／餐廳／課程名），不做枚舉。分類這件事由**池**承擔，
再加一層項目分類只是逼人每次多選一格。

## 2. 三個設計取捨

🔴 **待審不扣餘額**。待審就扣的話，退件之後餘額要回沖 —— 那是很容易對不起來
的帳。畫面另外顯示「審核中 $X」就夠了。

🔴 **超支的餘額是負的、轉紅**，不夾成 0。真的花超了，畫面就該講出來。

🔴 **登記即待審**，沒有草稿階段。owner 的流程就是「登記後我審核」，中間再插一個
草稿只是逼人多按一次送出。退回後本人改完會**自動回到待審**，不用再找送出鈕。

## 3. 兩個入口

| 誰 | 在哪 | 權限 key |
|---|---|---|
| 員工 | `/my.html` 的「福委會」卡（選池／填項目金額／送出／看自己的） | `me_benefits` |
| owner／HR | 人事管理 › 福委會（池、撥款、待審佇列、代登、送會計） | `hr_benefits` |

🔴 **自己登記的那幾筆不受 `money_view` 管**（同零用金 PETTY_CASH_PLAN §4）。
靠 **scope** 而不是抹鍵：`/benefits/me` 一族一律 `WHERE staff_id = 我`，
而 `staff_id` 只從 token 解（`resolve_current_staff`），永不收 client 傳的值。
給那幾支掛上 `money_dep` ＝ 沒有金額權的員工連自己登記了什麼都看不到。

**審核／匯款**另外要 `finance_approve`（審的是別人的錢，同零用金）。

## 4. 進公司請款＝沿用既有金流，一步都不自己造

核准 → 產一張 `CrmPaymentRequest`（`category=員工福利`、`payee_name=員工`、
`payment_status=應付款`）→ 自動出現在**應付帳款**。
匯款 → 那張應付款結清成一列 `CrmCashEntry`。

抄過來的四條規則（零用金的教訓，不可在這條路上重犯）：
- 核准**冪等**：已經有 `payment_request_id` 就不再產（重按不會變兩張）。
- 退回要**撤掉未付款的應付款** —— 不撤就是**幽靈負債**：登記回到本人手上、
  帳上還掛著那筆錢，月結與現金流預測都會多算。
- **已付款的不准撤** → 409，請走沖銷（那筆錢真的出去了，不是把歷史抹掉）。
- 匯款**不重複記帳**：已經有對應收支列的不再落帳。

## 5. 送會計

`GET /crm/benefits/accounting-package`（＋`.csv`）：每個池的**撥款／已用／餘額**
＋ 撥款逐筆 ＋ 支出逐筆。只收「已核准／已付款」—— 待審與退回還不是帳，
送過去只會讓人對不起來。

## 6. 刻意不做

- 職工福利委員會的法定那一套（提撥率、福委會選舉、法定申報）。
- 勞健保／勞退雇主負擔（那是薪資模組）。
- 「這筆要不要併入個人所得」的稅務分區 —— owner 的流程裡沒有這件事，
  2026-08-21 我自己加過一次，是多做的，已移除。真的需要時再談。

## 9. 三種形狀 —— 年度活動與健檢也要裝進同一區（2026-08-21 追加）

> owner 的原話：
>
> 「有些時候福利池會是一些**年度活動**像是這樣。」（LAZY KIT 券：有薪假 5 日
> ＋ 有薪假期間所有支出 10,000 內，限本人使用，效期 2026/01/01–12/31）
> 「我想要有一個**像是活動**，然後下面有**好幾個人的額度與有效期間**，
> 然後有一些**活動說明**。」
> 「有些是**健檢方案**⋯⋯我覺得可以就是一個**可以打字、附上文件的說明**。」

### 9.1 三個真實例子擺在一起

| | 快樂／進修 | LAZY KIT（年度券） | 健檢方案 |
|---|---|---|---|
| 額度屬於誰 | 全公司共用一桶 | **每個人各自 10,000** | — |
| 期間 | 不限，跨年度滾 | **2026/01/01–12/31** | 該年度 |
| 員工要知道的事 | 池裡還有多少 | 我的額度／期間 | **方案內容**（打字說明＋廠商的 PDF） |

現行模型只表達得出第一欄。

### 9.2 兩件事就夠了

一開始我規劃了三個正交的軸（額度／挑不挑方案／錢怎麼出），還為健檢設計了
方案表與「公司直接付廠商、多人合併成一張應付款」。**owner 把健檢收斂成
「打字＋附檔的說明」之後，那一整條線都不用做了** —— 連帶消失的還有兩個
本來最有風險的地方（合併請款的冪等鍵、退回時不能整張刪 AP 要減額）。

留下來的只有兩件：

| 加什麼 | 給誰用 |
|---|---|
| **每人額度＋有效期間** | LAZY KIT 這種「一人一份、過期不算」的年度活動 |
| **說明（打字）＋附件（檔案）** | 健檢方案（廠商 PDF）；LAZY KIT 也用得到（券的圖就是附件） |

所以只有一個軸：`quota` ＝ `shared`（共用桶，現況）／ `per_person`（每人一份）。
說明與附件**兩種都有**，不分模式。

🔴 健檢的錢怎麼付**先不進系統**。owner 描述它的方式是「一個說明」而不是
「一筆要請款的錢」—— 現在就替它設計金流，是替一個還沒發生的需求做設計。
真的要走系統時再談（那時的問題會是「收款人是廠商」與「多人合併一張」，
已記在 git 歷史裡）。

### 9.3 資料模型

`hr_benefit_pools` 加五欄（沿用現表，既有兩個池不用搬家，全部走預設值＝現況）：

| 欄 | 預設 | 幹嘛 |
|---|---|---|
| `quota` | `shared` | `shared` 共用桶／`per_person` 每人一份 |
| `description` | 空 | **說明**（給員工看的）。🔴 不共用 `notes` —— 那欄是管理者備註，混在一起兩邊都讀不乾淨（同 `reflection` 不共用 `notes` 的理由） |
| `attachments` | `[]` | 附件清單 `[{name, path, size}]`。健檢方案的 PDF、券的圖 |
| `valid_from` / `valid_to` | 空 | 有效期間。**留空＝不限**（共用池就是留空） |

附件用 JSONB 一欄不另開表：一個項目撐死三五個檔，開一張表要多一組 CRUD、
多一個 join，換來的只有「可以對附件下條件查詢」——而沒有人要那樣查。

🔴 **檔案存放與取檔沿用既有的那一條路**，不另造：存到 `settings.receipts_root`
底下 `_福委會/_說明文件/`，取檔走既有的 `GET /api/v1/crm/receipt-file?path=`
（那支已經有路徑白名單守衛）。上傳沿用零用金那兩道護欄：副檔名黑名單
＋ 串流上限。

新表 `hr_benefit_allowances`（每人額度）：
`pool_id` / `staff_id` / `staff_name`（快照）/ `amount` / `valid_from` / `valid_to` / `notes`

期間放在額度列上而不是只放在池上 —— 同一個活動有人是年中才到職、效期不同，
放在列上就表達得出來；不填就繼承池的期間。

🔴 **資格不做成規則，做成名單。** 「到職滿一年」「每兩年一次」這種條件一旦寫進
程式，就要永遠維護它的例外。額度表本來就是一列一個人 —— **誰有資格＝誰在名單上**，
owner 加一列就是給資格。要省事就做一顆「全部在職員工各加一列」的按鈕，
不要做規則引擎。

### 9.4 餘額：兩種算法，都進 `core/hr_logic.py`

- `shared`：`Σ撥款 − Σ(已核准＋已付款)`（現況，不動）
- `per_person`：`我的額度 − 我在期間內的(已核准＋已付款)`；
  池層另外顯示「已配 $X ／ 已用 $Y ／ 幾人還沒動用」
- 🔴 **超額的處理兩者不同**：共用池超支只轉紅不擋（那是公司該知道的事實）；
  個人額度超額要**擋**（422）—— 那張券本來就沒這麼多，讓它過去只是把問題
  推到請款那一關才爆。
- 🔴 **「待審扣不扣」兩者也不同**（實作時 e2e 才逼出來的）：共用池待審不扣
  是對的（桶子大、退件不用回沖）；但個人額度只有 10,000 時，那條規則會讓
  同一個人連送三筆 10,000 全部待審都不被擋 —— 擋超額形同虛設，等 owner
  一核准就爆了。所以每人額度另外算一個 `available ＝ 額度 − 已用 − 審核中`，
  **守衛看 available、畫面也顯示 available**（那才是「我還能再申請多少」）。
  退回就放回來，不牽涉別人，沒有回沖問題。
- 🔴 **期間外的登記也要擋**：券寫著 2026/01/01–12/31，2027 年拿去用就不算數。
  日期比對用 `local_day()`，不要直接 `strftime` —— timestamptz 讀回來是 UTC，
  這個 repo 已經被差一天咬過三次。

### 9.5 畫面

**管理端**（人事管理 › 福委會）：項目卡片多一個次要標籤（共用／每人）。
新增／編輯項目的表單多：類型、說明、期間、附件上傳。
選中之後底下的區塊依 `quota` 換：

- `shared` → 撥款表（現況）
- `per_person` → **額度表**（誰／多少／期間 ＋「全部在職員工各加一列」）

明細表共用。表格版面照固定欄寬那套（`<colgroup>` ＋ `table-layout:fixed`，
多餘寬度留給最後一欄）。

**員工端** `/my.html`：

- 每個項目都顯示**說明**與**附件連結**（健檢方案就是靠這個被看到）
- `shared` → 現況（池餘額＋我已用）
- `per_person` → 「我的額度 $10,000（2026/01/01–12/31）、已用 $X、剩 $Y」
