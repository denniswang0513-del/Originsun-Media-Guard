# 福利池（員工福利）— 規格正本

> 2026-08-21 起。owner 的原話只有兩句：「員工的請款與員工的福利 會要送到會計那」、
> 「要繼續執行福利池的任務」。以下的讀法與取捨是我下的，**有錯就改這份文件**。

## 0. 為什麼需要一個新東西（既有的哪裡不夠）

員工請款那條路（`docs/PETTY_CASH_PLAN.md`）已經很完整：登記單據 → 送審 → 核准
→ 產應付款 → 匯款 → 落帳成收支。但它的形狀是**核銷**：員工先墊錢、附收據、來報帳。

福利有一半不是那個形狀：

| 福利 | 形狀 | 既有零用金接得住嗎 |
|------|------|--------------------|
| 生日禮金、三節獎金、婚喪喜慶補助 | 公司**直接發給**員工，沒有收據 | ✗ 沒有單據可貼 |
| 健檢、教育訓練、員工旅遊 | 員工先付、憑收據核銷 | ✓ 形狀相同 |

而且兩者共通、零用金完全沒有的一欄：**這筆要不要併入員工的個人所得**。
那正是「送到會計那」真正要的東西 —— 會計要據此年底開扣繳憑單。

還有一件零用金不管的事：**額度**。福利是先編預算再花，花超過要看得見。

## 1. 範圍（做什麼 / 不做什麼）

做：
- 福利池＝一筆編列好的預算（可多池：年度福利、尾牙、旅遊…），有餘額。
- 動支＝從池裡撥給某位員工的一筆錢，兩種 `kind`：`給付`（直接發）／`核銷`（憑收據）。
- 每筆動支帶 `taxable`（是否併入個人所得）——會計交付的分區就靠它。
- 核准後**沿用既有金流管線**：產 `crm_payment_requests`（應付帳款）→ 匯款 → 收支明細。
- 會計交付包：按年/月匯出，分「併入個人所得」（按員工彙總，扣繳用）與
  「公司費用」（按項目彙總）兩區，另附池的編列與餘額。

不做（刻意）：
- 不做職工福利委員會那一套（提撥率、福委會選舉、法定申報）。公司規模用不到，
  真的要做是另一個題目。
- 不做勞健保／勞退雇主負擔 —— 那是薪資模組的事，不是福利池。
- 不自己算扣繳稅額。系統只負責把「哪些人、哪些筆要併入所得」講清楚，
  稅額由會計算（他們有申報軟體，我們算了也只是多一份要對的數字）。

## 2. 資料

### `hr_benefit_pools` — 池
| 欄 | 說明 |
|----|------|
| id / entity | 兩本帳（`docs/LEDGER_ENTITY_PLAN.md`）。福利是母公司的事，預設 parent |
| year | 年度 |
| name | 「2026 年度員工福利」「2026 尾牙」 |
| budget | 編列金額 |
| status | `open` / `closed`（結束的年度關起來，不再能動支） |
| notes / timestamps | |

### `hr_benefit_grants` — 動支
| 欄 | 說明 |
|----|------|
| id / pool_id | |
| staff_id / staff_name | name 是**快照** —— 人員改名不該讓歷史單跟著變 |
| category | 生日禮金／三節獎金／婚喪喜慶／健康檢查／教育訓練／員工旅遊／其他 |
| kind | `給付`（公司直接發，無收據）／`核銷`（憑收據） |
| amount / grant_date | |
| taxable | 0/1 是否併入個人所得 → 會計分區的唯一依據 |
| receipt_url | 核銷型才會有 |
| status | 草稿／待審／已核准／已付款／退回（與零用金同一組字，UI 與心智模型一致） |
| payment_request_id | 核准時產的那張應付款（硬連結，冪等靠它） |
| notes / timestamps | |

**餘額 ＝ budget − Σ(已核准 + 已付款)**。待審**不扣**餘額，但畫面另外顯示
「審核中 $X」—— 待審就扣的話，退件之後餘額要回沖，那是一種很容易對不起來的帳。

## 3. 流程（與零用金同構，刻意的）

```
草稿 ──送審──▶ 待審 ──核准──▶ 已核准 ──匯款──▶ 已付款
                  │                  │
                  └──退回──▶ 退回      └─（撤掉未付款的應付款）
```

- 核准 → 產一張 `CrmPaymentRequest`（`payee_name`=員工、`payee_type`=內部人員、
  `category`=員工福利、`payment_status`=應付款）→ 自動出現在應付帳款。
- 匯款 → 沿用零用金那條：`CrmPaymentRequest` 結清成一列 `CrmCashEntry`。
  **冪等靠 `payment_request_id`**：重按不會重複記帳。
- 退回 → 撤掉還沒付款的應付款。🔴 已付款的不准撤（那筆錢真的出去了）→ 409，
  請走沖銷。這條直接抄零用金的「幽靈負債」教訓。

## 4. 權限

新模組 key `hr_benefits`（人事管理群）。看得到自己那幾筆不需要它（own-scope，
比照零用金 `/petty/me`：`staff_id` 只從 token 解，永不收 client 傳的值）。
**審核與匯款**要 `money_view` + `finance_approve` 兩把（比照零用金：審核畫面
本身就是別人的金額）。

## 5. 會計交付

`GET /api/v1/crm/benefits/accounting-package?year=&month=`（可另出 CSV）：

1. **併入個人所得**：按員工彙總（姓名／身分證／筆數／合計）＋逐筆明細。
   會計拿這區開扣繳憑單。
2. **公司費用**：按項目彙總＋逐筆。不併個人所得的那些。
3. **池**：編列／已用／餘額。

身分證只從 `crm_staff` 帶一次（PII 單一正本，比照零用金 `_build_aps` 的作法）。
