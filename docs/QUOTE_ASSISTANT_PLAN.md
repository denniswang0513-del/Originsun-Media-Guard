# 對話式完成報價單 — 規劃正本

> 起因：owner 2026-09-09。原始需求是「報價單和 Discord 連結、跟電腦上的 LLM 互動」，
> 經過幾輪釐清後主線改成：**「客戶丟一堆訊息或截圖 → 跟 AI 問答討論 → 把報價單做完」**。
> Discord 降成之後可加的另一個入口（附錄 A）。
>
> 這份**尚未實作**。待拍板見 §10。文中所有效能數字都是 2026-09-09 在 master 上實測的。

## 1. 主線：一句話與流程

> 貼上客戶的訊息或截圖 → AI 整理成草稿並反問 → 你回答 → 草稿即時更新 → 你確認寄出。

```
你：（貼 15 則 LINE 訊息，或一張對話截圖）
AI：整理出 6 項。三件事要問你：
    1. 精華影片他前面說 2 支、後面改 3 支 —— 最終是 3 支嗎？
    2. 30 秒短影音報多少？（沒有歷史價）
    3. 要不要加專案管理費？
你：3 支；短影音 6000；管理費要加
AI：更新了。還缺付款階段，照慣例 3:4:3？
```

右邊那張草稿同步在變 —— **它就是 2026-09-09 做好的「自動存草稿」**，對話只是不斷 PUT 它。
你隨時可以停下來自己手改，或直接按寄出。

**第一則訊息就是「貼客戶的東西」**，所以不需要另外做一個「貼上產項目」的功能，那是這個對話的第 0 輪。

### 🔴 真正的瓶頸不是 LLM，是價目

2026-09-09 查生產庫：**歷史報價單 3 張（22 個項目）、報價範本 3 個（每個 3 項）**。

客戶只會說「我要兩支精華、一支長版」—— **價格是你的**，LLM 生不出來。所以：

- 對話式反而**解掉**這件事：它會問「這項報多少？」，你答了它就填；
- **答過的價順手存成價目**（§10 待拍板），下次它就自己帶；
- 換句話說：**用這套工具本身就是在建價目表**。前幾張會問很多，之後越問越少。

## 3. 為什麼是「對話式」而不是「一次到位」

一次到位（貼一坨 → 產完整報價）看起來省事，但真實情境裡：

- 客戶訊息**前後矛盾**（09/04 說 2 支、40 分鐘後改 3 支）
- 客戶**不會給價**
- 客戶**沒講但一定要報**的（管理費、字幕、修改次數、版權、交通、加班）
- 訊息裡混著閒聊與執行條件

這幾件事都需要「問一下」才能定案。硬要一次到位，結果是一張看起來完整、實際上要全部重看的報價單 ——
**比空白更危險**。

對話式最容易做壞的地方是「聊了 20 輪還是沒有東西」，所以本設計的核心是
**每一輪都在改同一張已存在的草稿**，不是聊完才產生。

## 4. 架構

### 4.1 資料

對話存在報價單上（`crm_quotations` 新欄位 `chat` JSONB，形狀同 bulletin 的 `conversation`）。
順便留下「這張報價是怎麼談出來的」，之後回頭看很有用。

> 新欄位記得在 `main.py` startup 的 `_crm_cols` 補一行 `ADD COLUMN IF NOT EXISTS`。

### 4.2 每一輪 LLM 回什麼（契約）

```json
{
  "reply": "給人看的話，繁體中文，兩三句",
  "patch": {
    "add":    [{"group_name":"", "description":"", "unit":"", "quantity":0, "unit_price":0}],
    "update": [{"n":3, "unit_price":6000}],
    "remove": [5]
  },
  "needs_price": ["還沒有單價的項目描述"],
  "questions":   ["要回頭問你或問客戶的，最多 5 題"],
  "terms_add":   ["要加進備註的條件"]
}
```

### 4.3 四條鐵則

1. 🔴 **patch 只能明確 add / update / remove，絕不整包覆寫。**
   項目照「大項目一組接一組」攝平後從 1 編號，`update.n`／`remove` 用的就是這個編號
   （前後端同一套；送出前先 flush 自動存，順序才對得上）。不然聊到第 8 輪，它會把你第 3 輪手動改好的單價默默洗掉 ——
   跟「整包 `model_dump()` 寫回把欄位洗掉」是同一種坑（`update_quotation` 那條前例）。
2. 🔴 **價格不由 LLM 決定。** 它可以說「上次類似的報 26000」，但要進 `needs_price` 等你確認才寫入。
   **報價單填錯價的代價遠大於少填一項。**
3. **它要主動問，一次問一批**（3～5 題、每題可跳過），不要一句一句像審訊。
4. **收斂條件明確**：每項有價 ＋ 付款階段有了 ＋ 沒有未回答的必問題 → 它說「可以了」。
   狀態仍留**草稿**，**寄出永遠是人按的**（對話介面不提供寄出）。

### 4.4 放哪

- 後端：`POST /quotations/{id}/chat`（背景跑、前端輪詢，同 bulletin），
  patch 套用寫成純函式 `core/quote_chat.py`（可單元測，不碰 I/O）。
- 前端：報價彈窗加一個對話面板（桌機）；手機版 `/m/` 報價卡上一顆「AI 助理」開全螢幕對話。
- **兩邊同一組後端**（`/quotations/{id}/chat`、`/price-items/match`）、同一支 patch 純函式
  （`js/shared/quote-patch.js`）—— 介面兩套、規則一份。

## 5. 截圖那條路

### 5.1 實測：claude 讀得懂

`claude --print --permission-mode plan`（唯讀）直接吃本機圖檔路徑：

| 測試 | 結果 |
|------|------|
| 1600×1000 中文 UI 截圖 → 讀出項目、單價、含稅總額 | **19.7 s，全對** |
| 縮到 800×500 | 15 s，數字全對（「後期」誤讀成「後製」） |
| 縮到 432×270 | 52 s，仍全對 |

讀圖比純文字那輪還快（輸出短）。可以一次貼多張，每多一張多幾秒。

### 5.2 前端零改動

`paste-image.js` 是 document 層的全站貼上攔截 —— 任何 textarea（含之後才動態長出來的）
Ctrl+V 就上傳 → `POST /api/v1/paste_upload` → 轉 WebP、剝除中繼資料 → 存共用圖床 →
內容裡留 `paste:<32 hex>.webp`。**對話框就是個 textarea。**

後端要補的只有：token → 本機路徑（`core/assets_host.assets_target()`）→ 交給 claude。

### 5.3 🔴 坑一：解析度

`api_paste._MAX_SIDE = 1600`。一般手機截圖（1080×2400 → 720×1600）沒問題；
**拼接的長截圖**（1080×6000 → 288×1600）字會剩 8px。
→ 報價這條路**另存一份原圖**，或這個命名空間的上限拉高。反正只是給 AI 讀，不佔多少空間。

### 5.4 做完自動刪圖（owner 2026-09-09 拍板）

截圖含客戶大頭貼、姓名，側邊欄可能還有別的對話 —— 用完就刪。

- **主要觸發**：報價狀態離開草稿（寄出）→ 刪掉這張報價 `chat` 裡引用的所有 `paste:` 圖。
- **兜底**：`core/scheduler.py` 每日掃「草稿超過 30 天、有 chat 圖」的報價一併刪
  （否則永遠沒寄出的草稿會把圖留著）。
- **對話紀錄保留**，但被刪的 token 換成「（截圖已刪除）」佔位，不要留死連結。
- 刪除要寫進 log（誰的、幾張、什麼時候），不要無聲消失。

> ⚠️ `core/assets_host.py` 目前**只有** `assets_target(namespace)`，`api_paste.py` 只有
> config + upload —— **沒有任何刪除路徑**。要新增一支 `assets_delete(namespace, filename)`，
> 並且只准刪 `paste:` 命名空間、只准刪這張報價自己引用的檔（別做成通用刪檔端點）。

## 6. LLM：主力 claude，Ollama 當備援

截圖需求出現後這件事就定案了 —— **你裝的 5 顆 Ollama 模型全是純文字，沒有 vision**。
要本機讀圖得再裝 llava／qwen-vl，6 GB VRAM 勉強塞得下但中文 OCR 差一截。

同一段報價需求的 A／B：

| | claude | llama3.1 8B（本機） |
|---|---|---|
| 耗時 | 7.0 s | 30 s（含冷載 9 s） |
| 客戶名 | 遠見 ✓ | **漏抓（空白）** |
| 數量 | 全對 | 「兩天」抓成 1 |
| 單價 | 全對 | 一項變 0 |
| 本機資源 | **不吃 CPU/GPU** | 吃 ~4.7 GB VRAM |

**Ollama 保留兩個角色**：claude 掛掉時降級（回覆標「本機模型草稿，請多檢查」）、
以及**內部成本／毛利那類不准外流的分析**（不出這台機器）。呼叫要帶 JSON schema 約束，
不要靠 prompt 拜託它回 JSON。

### 6.1 模型可選（零重構）

CLI 的 `--model` 吃別名（`fable`／`opus`／`sonnet`／`haiku`）或完整型號。
`_call_claude(prompt, extra_args=["--model", "sonnet"])` —— `extra_args` 本來就在
（公布欄「問 Claude」拿它傳 `--permission-mode plan`）。

目前預設是 `~/.claude/settings.json` 的 `"model": "opus[1m]"`。

**建議**：抽結構化這種短活用 sonnet；opus 留給要推理的（企劃書、SEO 長文、產業情報）。
**不要用 haiku** —— 實測比 sonnet 慢一倍（見 §7）。

更進一步：開一組 settings `ai.models.<用途>`（`quote_chat` / `seo` / `social` / `ask`…），
預設寫在碼裡、後台可調，換模型不用發版。這比較符合其他開關的慣例。

⚠️ 別為了省額度把需要長 context 的用途（整批 30 個作品的 SEO）也降到小模型 —— 那會變成品質問題。

## 7. 效能實測（2026-09-09，master）

用模擬真實情境的 prompt（客戶三天內 15 則零散 LINE 訊息，含「2 支改 3 支」的矛盾）：

| 量的東西 | 時間 |
|---|---|
| CLI 固定開銷（送 "hi"） | **6.8 s** |
| 第 1 輪：15 則訊息 → 6 項 ＋ 5 問 ＋ 5 條備註 | **34.5 s** |
| 第 2 輪：帶對話歷史＋草稿＋你的回答 → 更新 | **33.0 s** |
| 同樣第 1 輪但用 haiku | **74.6 s** |
| 讀一張截圖 | **19.7 s** |

**每輪 33～35 秒，不太隨對話變長而增加**（第 2 輪輸入是第 1 輪的 1.7 倍，時間反而略降）——
時間花在產出，不在讀輸入。

一張報價的體感：

```
貼訊息／截圖        你 ~30 秒
輪1 整理            等 35 秒
讀問題、回答        你 1–2 分鐘
輪2 更新            等 33 秒
檢查、微調價格      你 1–2 分鐘
輪3 補付款階段      等 33 秒
最後手改 + 寄出     你 1–2 分鐘
─────────────────────────────
合計 5–8 分鐘，其中等 AI 約 1.5–2 分鐘
```

### 7.1 等待期間畫面要一直在動（2026-09-09 已做）

串流雖然接了，但**前 35 秒左右畫面什麼都不會動** —— 那段看起來就像當掉。
`js/shared/quote-wait.js`（桌機手機共用的純函式）給三樣**真實**的東西，不做假進度條：

1. **點會跳**（處理中 → 處理中. → .. → ...）—— 證明頁面還活著
2. **秒數會走**，超過 10 秒補一句「通常 30–50 秒」，超過 50 秒改成「比平常久，還在跑」
3. **「排隊中（前面還有其他 AI 工作）」** —— 後端 `_chat_stage` 的真狀態：
   互動式的閘只有 2，撞到夜間 SEO 批次是真的在排隊，那時該講實話

每秒只換那一小段字（不整包重繪，否則捲軸會被拉回底、畫面會閃）。
實測一輪 42 秒內文字變了 37 次，38.4 秒接上串流。

### 7.2 讓等待不痛的三件事

1. **串流** ✅ 已做：`--output-format stream-json --include-partial-messages`，邊產邊顯示。
   🔴 **實測只提早 5–7 秒**（37.2 秒開始出字／44.0 秒落地；另一次 47.2／51.9）——
   不是原本猜的「2 秒就有字」。時間大半花在 claude 的 agent 前置作業，真正吐字很快。
   仍然值得做（有字在動 vs 盯著轉圈差很多），但別期待它把 40 秒變 2 秒。
2. **背景跑 + 輪詢**（bulletin 那套現成）：送出後可以先去做別的。
3. **要求 patch 只帶改動欄位**：第 2 輪它回了整包 2.5 KB，砍掉一半 → 每輪可望降到 20 秒內。

### 7.3 🔴 併發閘只有 2

`_CLAUDE_GATE = asyncio.Semaphore(2)`，而 `_call_claude` **已經有 11 個檔案在用**
（作品 SEO、文章 SEO、翻譯、社群、產業情報、公布欄問 Claude、財務卡、參考片庫、企劃書、作品集…），
排程集中在凌晨 3:00／08:30／09:00。

互動式呼叫撞到夜間批次會排隊（SEO 一筆 ~25 秒 × 30 個作品 = 十幾分鐘）。
→ **互動式要給獨立的閘或優先權**，別跟批次共用。

## 8. 安全與資料界線

1. **報價內容會離開這台機器。** 目前 claude 在本系統處理的都是對外內容（官網 SEO、社群、情報）；
   這條線改成處理**客戶名、案名、金額**。
   → prompt **只帶你貼進去的東西**，不要把庫裡的客戶清單、歷史報價、`internal_cost` 一起塞進 context。
2. **內部成本／毛利不進 prompt**，要分析走 Ollama。
3. **截圖用完就刪**（§5.4）。
4. **單點故障**：CLI 登入狀態掛了（訂閱到期／登出／CLI 更新），不只報價死，SEO／翻譯／社群一起死。
   已有 `ai_runner_failed` 告警，但那是連續失敗後才發。
5. **master gate**：機隊 9 台跑同一份碼，只有 master 有 claude —— 照
   `services/website/social_runner.py` 的慣例加 `core.topology.is_master_machine()`。

### 實作時踩到、值得記住的兩件事
1. 🔴 **FastAPI 的 `background.add_task` 是串行的**：寄出時第一支是 Playwright 產 PDF，
   它慢或炸掉，後面的清圖與收價就整串不跑（而且靜默）。改用 `core.bg_task.fire()` 各跑各的。
2. 🔴 **`_load_items()` 回的已經是 dict**（它自己套過 `_item_to_dict`）——再包一次會
   AttributeError，包在背景任務裡就是靜默失敗。端對端驗收才抓得到這種。
3. 🔴 **編輯既有報價時自動存是關的**（`_autoReset(!quotation)`，刻意的：怕靜默改到舊資料）——
   所以 AI 的 patch 與「用價目補上」只呼叫 `_autoTouch()` 會**只改畫面、關窗就丟**。
   那兩條路改走 `_saveAiChange()`：使用者按出來的、畫面也變了，不寫回去才是丟資料。
4. 🔴 **`--model <值>` 是命令列參數**：前端送什麼就接什麼等於讓瀏覽器往 CLI 塞旗標。
   一律過 `quote_chat.pick_model()` 的白名單。
5. 🔴 **`update_quotation` 對 `tax_rate`／`final_price`／`payment_stages`／`terms` 是無條件覆寫**
   （那幾行不看 `model_fields_set`）——手機那支 PUT 少帶一個欄位就是靜默清掉它。
6. 🔴 **原始碼裡不要出現 `image` 加斜線星號**：`_srcscan.js_code_only` 會把它當成區塊註解
   的開頭，到下一個「星號斜線」之間的程式碼整段消失，掃原始碼的測試就看不到那些函式。
   （手機那支的 `accept` 因此改成在 JS 裡設。）

## 附錄 A：Discord（之後可加的另一個入口）

原始需求裡的 Discord 沒有消失，只是**不該第一個做** —— 如果客戶訊息來自 LINE／Email，
Discord 只是個「貼字的地方」，那不如直接貼進報價彈窗，省掉 bot token、帳號對映、master 關機的問題。

Discord 值得做的情境是：**你們真的在 Discord 討論這些案子** —— 那時 bot 能直接讀整串 thread，
不用複製貼上。介面不同，後面接的是同一個 `chat` 欄位。

真要做的話：

- **走 Bot Gateway 長連線**（不是 HTTP Interactions）：bot 自己連出去的 WSS，
  **不用對外開埠、不用動 Cloudflare**，資料留內網。
  HTTP Interactions 要公開 URL ＋ Ed25519 簽章 ＋ 3 秒內回應 ＋ 在 `core/public_access.py`
  登記免登入面 —— 多一個對外攻擊面，換不到什麼。
- 🔴 **master gate 必須有**：9 台各連一個 bot ＝ 一則指令回 9 次、建 9 張草稿。
- **`users.discord_id`**（照 `google_id` 的形狀）＋ **bot 用那個人的權限打 API**，
  沒有 `crm_quotes` 就查不到 —— Discord 不能變成繞過 RBAC 的後門。
- 依賴 `discord.py`：🔴 生產 8000 跑的是 `python_embed` 不是 `.venv`，要手動 pip 並記進
  `requirements_server.txt`，否則發版後 bot 靜默不啟動。
- 另一條路是 NAS 上那個 n8n（有 Discord node、改流程不用發版），但權限判定、金額計算、
  草稿版本號都在 master 的 Python 裡，n8n 只能再打一次我們的 API —— 多一跳、多一份憑證。
  除非要讓非工程師自己改流程，否則不划算。

**通知**（報價寄出／客戶點開 `/q/{code}`／簽核／有效期剩 3 天）是另一件小事，半天：
`notifier.py` 加一條 `discord` 通道即可。其中「客戶點開了」最有商業價值，但
`/q/{token}` 目前**不記瀏覽** —— 要在 `crm_quotations` 加 `first_viewed_at` / `view_count`。
