## 2. 規則契約

### 2.1 規則 N — 名稱以母帳為主

| | |
|---|---|
| 生效條件 | 私帳案**恰好**連到 1 個母帳案 |
| 動作 | **顯示層**取母帳案名 |
| 不做 | **不改寫 `crm_projects.name`** |
| N:1 | 不套用，改標「連結 N 個母帳案」並列出母帳案名 |
| 母帳改名 | 顯示自動跟著（讀取時取，不快取） |

🔴 **為什麼不做破壞性改名**（兩個理由，任一個都足以否決）：

1. Sheet 工時的 `resolve_project()` 是用 `project_name` 查 `load_project_lookup()`
   的名稱索引。把私帳案名改成母帳案名，之後 Sheet 新進的列就對不到案
   （既有列的 `project_id` 已寫入，不受影響，所以症狀會延遲一週才出現）。
2. 私帳案名是 owner 自己的語彙（「開村影片」對「蟾蜍山｜煥民新村 館所介紹」），
   改掉之後找不回來，而收支明細、對帳、匯入預覽都還在用它認案。

私帳原名在詳情頁以小字保留（「私帳原名：開村影片」）。

**唯一正本**：`core/ledger_project.py` 新增
```python
def linked_display_name(mine_name: str, parent_names: list[str]) -> tuple[str, str]:
    """回 (顯示名, 副標)。1:1 → (母帳名, 私帳原名)；其餘 → (私帳名, "")。"""
```
所有輸出私帳案名的地方都要走它。M1 的第一步就是把這些地方掃出來，
候選（起草時掃到的）：

- 後端：`routers/api_finance_projects.py`、`routers/crm/projects.py`、
  `routers/api_crm_mobile.py`、`routers/crm/cash.py`
- 前端：`frontend/tabs/finance/subviews/projects.js`、`household.js`、`recon.js`、
  `frontend/tabs/crm/crm-cashbook.js`、`crm-projects-detail.js`、`crm-projects-pay.js`

掃描要收成測試（見 §6），否則之後新增一個顯示點就漏一個。

### 2.2 規則 A — 母帳沒金額就先填私帳的

| | |
|---|---|
| 生效條件 | 母帳案 `contract_amount` 為 NULL 或 0，**且** 1:1，**且** 私帳案金額 > 0 |
| 動作 | 寫 `contract_amount = 私帳金額`，同時記 `contract_amount_source='mine'` |
| 解除 | 任何人在母帳手動改過金額 → `contract_amount_source` 清空，之後**永不**再被私帳覆蓋 |
| N:1 | **不自動填**（多個母帳案共用一個私帳金額，填了會重複計）→ 進「待確認金額」清單請人工填 |

🔴 **這個數字是下限占位，不是真值**：私帳金額是「我拿到的那段」，公司跟客戶的
合約額一定 ≥ 它（現有 12 組的落差是 3～17 倍：開村影片 63,000 vs 蟾蜍山 400,000、
2026 臺北城市形象片 96,000 vs 1,600,000）。所以：

🔴 **已驗的副作用 —— 兩個報表要排除佔位案**：

- `services/finance_statements.py:902` 的母公司「專案毛利」儀表板只取
  `contract_amount > 0` 且 `not_mine` 的母帳案。佔位金額進去 → 那案的成本
  是公司的全額、收入卻是我拿到的那段 → **毛利看起來極差甚至負數**，
  而且會把儀表板的 top/bottom 排名整個帶歪。
- `routers/api_cashflow.py:154` 用 `proj.contract_amount` 當預測總額 →
  現金流預測會低估。

兩支都加 `contract_amount_source != 'mine'` 的條件，直到人工確認。
（`core/finance_logic/_statements.py:504` 的權責損益吃的是**私帳**案的
`contract_amount`，不受這條影響。）

**UI**：母帳專案頁金額欄位旁標「暫填自私帳・待確認」；另給一張
「待確認金額」清單（`contract_amount_source='mine'` 的全部母帳案），
點進去可直接改。改完標記自動解除。

**唯一正本**：`core/crm_logic.py` 新增
```python
def placeholder_contract_amount(parent_amount, mine_amount, parent_count) -> int | None:
    """要不要用私帳金額當母帳的佔位。回 None＝不填。"""
```

## 4. 母帳沒開案的補建

私帳 415 案裡，母帳根本沒開專案的佔絕大多數。**不是每一案都該補**，
判別鍵是**這案的錢有沒有經過公司**：

| | 錢的流向 | 母帳該不該有案 | 做法 |
|---|---|---|---|
| a | 客戶→公司→我（公司發包給我） | 該有 | 補建 + 連結，母帳為主 |
| b | 客戶→公司（公司自己做，只是沒建專案） | 該有 | 補建（母帳自己的漏，與私帳無關） |
| c | 客戶→我（我自己接自己收） | **不該有** | 私帳為主，母帳不要碰 |

自動判別：私帳案 × 母帳發票／收款，比對「客戶（經 `clients.crm_link_id`）
＋ 期間 ＋ 金額」。對得上 → a/b；對不上 → c。

🔴 **c 類絕對不能進母帳**：那些錢公司從來沒收過，補進去會讓母帳的營收、
客戶績效、應收全部虛增。

補建的案要標 `origin='backfill'`（或等價標記），不進今年的管線、成案率、
客戶狀態自動化，否則幾百案灌進來會把 CRM 的統計打亂。

## 8. M6 —— 雙向「推送」＋連結後以母帳為準（規劃，2026-09-12）

> owner 2026-09-12：「我希望私帳母帳可以連結。有時候我在私帳建立專案，但希望可以
> 推送到母帳；我在母帳建立專案，可以推到私帳。兩邊的專案表一樣都可以（以母帳為準）。」

### 8.1 現況：同一件事散成四顆按鈕、三種語意

| 按鈕（在哪） | 真正做的事 | 端點 |
|---|---|---|
| CRM 專案詳情「推送至私帳／搬回公司帳」 | **搬家**：改 `entity`，一案只在一本 | `move-ledger` |
| CRM 專案詳情「連結私帳」 | **分身＋鏡射金額**：私帳多開一案、收入＝掛給我的成本行；沒有成本行就 409 | `mirror-to-mine` |
| 私帳執行專案詳情「⬆ 推專案管理」 | **旗標**：`crm_pushed=1`，讓私帳案出現在母帳管線（沒有母帳列） | `PUT /project-ledger` |
| 財務 › 專案對應（兩個方向）「連結／建立／解除」 | **純對應**：建對面的分身並連結，錢不搬 | `parent-create`／`parent-link`／`mine-create`／`mine-link` |

owner 要的「推送」＝第四種（建對面的分身並連結），但它只住在財務頁的對應表，
專案頁上兩顆叫「推送／連結」的按鈕反而是別的東西。

生產實查（2026-09-12，唯讀）：母帳 263、私帳 416；連結 30 組（新形狀 26、只有舊
形狀 4、N:1 1 組）；`crm_pushed=1` 的私帳案 6；26 組新形狀連結裡客戶不同 17、
案型不同 5、狀態不同 3、結案日不同 6（其中 5 組是母帳空白私帳有）。

### 8.2 契約

**推送 ＝ 在對面建一個對應的案並連結；兩案並存、各記各的錢。** 一個字：分身。

| 方向 | 帶過去什麼 | 金額 |
|---|---|---|
| 私帳 → 母帳 | 案名、客戶（私帳客戶→母帳客戶，沒有就建並連結）、案型、結案日、說明 | 母帳合約額＝私帳的，標 `contract_amount_source='mine'`（§2.2 既有規則，待確認） |
| 母帳 → 私帳 | 同上 | 私帳營收＝掛給我的成本行加總（`mirror_lines`），一筆都沒有就 0、**不擋** |

**以母帳為準 ＝ 連結後，識別欄由母帳決定。** 識別欄清單（`LINK_SYNC_FIELDS`，唯一正本放
`core/ledger_project.py`）：`client_id`、`project_type`、`status`、`shoot_date`、
`start_date`、`completion_date`、`description`。

三條規則（把 §2.1 顯示名、§2.2 金額那兩條的精神套到全部識別欄）：

1. **母帳有值 → 私帳跟著**：連結當下複製一次；之後母帳 `PUT /projects/{id}` 改了
   任一識別欄，同一交易寫進連結的私帳案。
2. **母帳空白 → 不清私帳**，而且連結當下反向補進母帳（母帳 216 案沒結案日、
   私帳全部有，是私帳補母帳不是母帳洗私帳）。
3. **N:1 不同步**（一個私帳案承接多個母帳案，母帳互相矛盾時不猜 —— 同顯示名規則）。

**不同步的**（刻意）：
- `name`：維持顯示名鏈（`crm_projects.name` 是 Sheet 工時對映的查表鍵，§2.1）。
- **所有金額欄**：母帳 `contract_amount` 是公司跟客戶的合約額，私帳的是「我拿到的那段」，
  同一個欄位兩種意思，差 3～17 倍（§2.2）。錢的橋只有一座：母帳成本行 → 私帳收入（鏡射）。
- 成本行／派工／報價／里程碑／備份三根：只住母帳，私帳的逐案損益本來就即時讀它們（CRM_BACKED）。
- 工時：owner 2026-09-05 擱置。

### 8.5 風險與已知取捨

- 🔴 **私帳案一旦連結就從 CRM 清單消失**（既有規則：`source_project_id IS NULL` 才列）。原本 `crm_pushed=1` 出現在管線的私帳案，推送到母帳後改由母帳分身出現 —— 派工／里程碑要在母帳那一列做。要跟 owner 講清楚。
- 🔴 **狀態同步會把「歸檔」帶進私帳**（母帳 213 案是「歸檔」，私帳只有結案／製作）。私帳側狀態是純顯示，不影響任何算法，但畫面上會出現新字。要不要把狀態排除在 `LINK_SYNC_FIELDS` 外，待 owner。
- 客戶：113 個私帳案已直接掛 CRM 客戶，所以「母帳客戶寫進私帳案」有先例；但 17 組既有連結客戶不同，第一次套用會把私帳客戶換成母帳客戶（私帳客戶對應表已連結的那些等價）。

- 金額**永遠不動**這條要釘測試：`sync_from_parent` 對 `contract_amount`／`ledger_detail`／`amount_*` 零觸碰。

### 8.7 記錯帳本（owner 2026-09-12「有時候我會把母帳當私帳記，然後才想到要推到私帳」）

這跟「推送」是**不同的病**，藥也不同 —— 所以「推送到私帳」的彈窗要先問一句
「這一案是哪一種」，而不是要 owner 自己知道要按哪一顆：

| 情況 | 正確動作 | 為什麼 |
|---|---|---|
| 公司的案、只有一部分是我的（公司付我後期費） | **推送**（分身） | 母帳留著跟客戶的合約，私帳只記我那段 |
| **整個案其實是私帳的**，只是在 CRM 建錯地方（公司根本沒有這個案） | **換帳本**（`move-ledger`，既有） | 一案只該在一本；分身會讓公司多一個不存在的案（毛利、管線、現金流全被它帶歪） |

換帳本本來就是為這個情境留的（全 repo 唯一的換帳本例外），**不能拿掉**；要補的是三件事：

1. **入口合一**：「推送到私帳」彈窗第一層兩個選項 ——「公司的案，我做其中一部分（推送分身）」／
   「整個是私帳的案，記錯帳本了（換帳本）」。第二個選項走現有 `ledger-move-check` → 換帳本。
   動作列上原本獨立的「推送至私帳」按鈕併進來（改名「換帳本」留在彈窗裡，不再是獨立按鈕）。
   私帳側同理：「推送到母帳」彈窗也給「整個是公司的案，記錯了（搬回公司帳）」。
2. **搬到私帳要把私帳需要的欄位補齊**（現在 `move_project_ledger` 只改 `entity`／`crm_pushed`）：
   - 問**案源**（源日／代開發票／自接…）—— 私帳的代辦費規則靠它（`apply_source_fee`）；
   - `ledger_detail` 走 `norm_detail`（成本行不動，它們本來就跟著專案走，CRM_BACKED 會即時讀）；
   - 🔴 **`resync_receivable`** —— 漏了那一案就安靜地不進私帳應收帳款（同 2026-08-26 那 349 案 NULL 的病）。
     現在的換帳本正是漏了這一步。
   - 反向（搬回公司帳）：清 `contract_amount_source`、`crm_pushed=0`（既有）。
3. **被擋住時講清楚是哪一種**（有收支／發票／請款掛在上面就 409）：
   - 錢已經從**公司帳戶**進出過（母帳收支是對帳單對過的）→ 這是公司的案，該走**推送**不是換帳本；彈窗直接給「改用推送」。
   - 真的記錯的單據：列出那幾筆（帶連結），要 owner 先去改單據。**不自動搬單據** ——
     兩本帳的帳戶、分類樹都不同，私帳已收又是增量制（`_sync_mine_project_received`，
     見「私帳已收被加兩次」），搬了就是重算一次的地雷；發票、請款在私帳依規則根本不該存在
     （私帳不開發票、私帳不跟公司請款）。

搬家會帶走的（沒有 `entity` 欄、跟專案走）：成本行、雜支、派工、報價、里程碑、備份三根、官網上架。
擋住的只有三張帶 `entity` 的：收支、發票、請款（`_LEDGER_BLOCKERS`，不變）。

### 8.8 我的案有三種收錢方式，三種各對一條路（owner 2026-09-12「有時候我只是拿專案費用，有時候走發票代開」）

| 收錢方式 | 案子住哪 | 錢怎麼走 | 系統上的路 |
|---|---|---|---|
| **拿專案費用**（公司的案，公司付我後期費） | 母帳（公司跟客戶的合約） | 母帳成本行掛給我 → 私帳收入（案源＝源日） | **推送（分身）** |
| **走發票代開**（我的案，客戶要發票，公司幫我開） | **私帳**（案源＝代開發票，代辦費自動 8%） | 母帳一張「內部代開」發票掛到**私帳案**（既有規則 `MINE_LINK_INVOICE_CATEGORY`），客戶匯進公司 → 自動生一張應付給我的請款單（92%） | **不需要母帳案** |
| 純私帳（自接／現金） | 私帳 | 只有私帳 | 只有私帳 |

「記錯帳本」最常見的就是第二種：先在 CRM 建了母帳案，發票也掛上去了，才想到它其實是代開的私帳案。
所以 8.7 的換帳本要再放寬一點，**換帳本到私帳時**：

- `_LEDGER_BLOCKERS` 對**發票**只擋 `category != 內部代開` 的（內部代開本來就准掛私帳案，`_assert_project_link`）；
  對**請款**只擋沒有 `source_invoice_id` 的（代開自動生的那張是公司要匯給我的錢，掛在私帳案上是正常形狀，生產已有）。
  收支照擋（那是公司帳戶的錢）。
- 掛著「專案」類發票被擋時，訊息講清楚：「這張發票是專案類 —— 如果客戶走的是代開，先到發票把類別改成內部代開再搬」
  （不代改：改類別會觸發代開自動化生請款單，那是錢的副作用，要人按）。
- 搬過去時案源預設：身上有內部代開發票 → 「代開發票」；否則問（源日／執行業務所得）。`apply_source_fee` 跟著算代辦費。

「推送到私帳」彈窗第一層因此是三選一（代開那一項底下再分兩條）：
1. 公司的案，公司付我一部分 → 推送分身（案源＝源日，收入＝掛給我的成本行）
2. 我的案、客戶走公司代開發票 →
   - **公司也留一份帳**（owner 2026-09-12 加的）：分身、案源＝代開發票、**收入＝母帳合約額**
     （那張內部代開發票的面額就是他的錢；掛給他的成本行通常是 0）、代辦費自動算；
     重新同步只更新工項，不翻案源、不動金額（`mirror-to-mine` 的 `source` 欄）
   - 整案搬到私帳 → 換帳本（案源＝代開發票，發票留在母帳掛過來）
3. 我的案、沒有經過公司 → 換帳本（案源問一下）

### 8.9 收款方式欄位（owner 2026-09-13「表單新增一欄標示收款方式，用這個切換代開與專案的狀態」）

8.8 的三選一彈窗改成**表單上一個下拉**（`crm_projects.billing_mode`，母帳用；私帳沒這欄、不在 `LINK_SYNC_FIELDS`）：

| 值 | 中文 | 意思 | 儲存時系統做什麼 |
|---|---|---|---|
| `company`（NULL 視同它） | 源日專案 | 公司的案 | 跟後期沒有自動連結；公司付你一部分再按「推送到私帳」→ 直接分身（不再問） |
| `passthrough` | 後期代開 | 你的後期案、客戶走源日代開發票 | **儲存即**在私帳建對應的案（案源＝代開發票、收入＝母帳合約額、代辦費自動）；發票預設「內部代開」（`_is_passthrough`） |
| `cash` | 現金收款 | **源日收現金**（owner：「這裡是源日的收款狀態」） | 不碰後期；只是標籤 |

切換規則（`routers/crm/project_links.apply_billing_mode`）：換值只動分身的**案源與代辦費**（代開發票 ↔ 源日，重跑 `apply_source_fee`），
不動私帳那邊手改過的金額與工項；換回 company／cash 分身**留著**（要拿掉走解除連結）。只有看得到私帳的請求會動私帳那一列，
別人存了只存欄位（回 `skipped` ＋ warning），帳本主人再存一次同一個值會把分身補建起來。
既有資料回填：身上有內部代開發票的母帳案 → `passthrough`，其餘 NULL（`db/migrations.CRM_INDEXES` 那條 UPDATE，冪等）。

「後期連結」＝表單／詳情上一行**唯讀的系統備註**（`core.ledger_project.link_note` 純函式產 `text`，前端只畫）：
連到哪一案、案源、收入、代辦費拆解（稅金＋買發票）、已扣／未扣、私帳落後了沒、上次同步（`ledger_detail.mirror_at`）、內部代開發票幾張。

「代辦費已扣除」（`ledger_detail.fee_deducted`，缺鍵＝True、只在 False 落庫）：owner 的定義是**營收仍是合約額，應收先扣掉代辦費**
（＝源頭代扣，現行預設）；取消勾選＝那筆費用沒先扣、全額會匯進來、應收＝營收（`client_wire`／`expected_cash_in` 看 `withheld_total`）。
代辦費金額 2026-09-13 起可手改（`invoice_fee` 進 `MANUAL_FIELDS`，同個人稅款那套：改過就凍住、改回試算值交還自動；稅金照算、買發票＝代辦費−稅金）。
母帳財務摘要只多一句「此案為後期案，公司實際收入＝代辦費 N」（`company_income`），毛利／管線算法不動（owner 第 4 點）。
