# 收支明細的分類 — 規格與 2026-08 大清理的判準

> 2026-08-22。這份同時是**規格**（新收支該歸哪一類）與**紀錄**（那一輪改了什麼、
> 依什麼證據）。之後回頭問「這批當初為什麼這樣改」，答案在這裡。

## 0. 一句話

```
銀行摘要文字 →〔bank_import_rules〕→ 類別 →〔finance_category_map〕→ treatment → 三表
```

左半邊使用者可編（財務管理 › 收支明細 › **🔍 對帳系統** › 分類規則），
右半邊也是（科目與設定 › 類別對映表）。**類別本身不是重點，treatment 才是。**

## 1. treatment 決定三件事

| treatment | 進損益？ | 進現金流？ | 用在哪 |
|---|---|---|---|
| `direct_income` / `direct_expense` | ✓ | ✓ | 一般收入與費用 |
| `ap_settlement` / `ar_settlement` | ✗ | ✓ | 結清請款單／發票（權責已在別處認列） |
| **`passthrough`** | **✗** | **✓** | **代收代付：錢不是我們的** |
| `transfer` | ✗ | **✗** | 帳戶間互轉（本金是內部移動） |
| `loan` | ✗ | ✓（走科目 cf_activity） | 貸款撥款／繳款 |
| `advance` | ✗ | ✗ | 員工預支本金 |

🔴 **`passthrough` 與 `transfer` 的差別是這整份文件的核心**：
兩者都不進損益，但 `transfer` **不計入現金流**（因為兩腳互抵），
`passthrough` **計**（錢真的進出了公司帳戶）。

把「代收代付」記成「轉存」＝ 餘額動了、淨流沒動 → **每一筆都製造一筆勾稽差額**。
2026-08 清理前，全期間累積 **624,511** 的差額幾乎全是這個原因。

## 2. 這家公司實際會遇到的類別

| 類別 | treatment | 什麼時候用 |
|---|---|---|
| `代收薪資` | passthrough | **股東匯薪水進公司**（含眷屬健保）。這些員工是股東自己養的，只是透過公司發放 |
| `代發薪資` | passthrough | **公司把薪水匯給員工**。🔴 不是「薪資」費用 —— 不是公司的人 |
| `發票代開` | passthrough | 代開發票的資金腳（收客戶的錢、匯給代開人、手續費匯入） |
| `代收代付` | passthrough | 幫別人（動工、木子映像…）代收代付 |
| `現金代收` | passthrough | 客戶付現、由人代收後存入，之後要轉出去 |
| `轉存` | transfer | **真的**在自己兩個帳戶之間搬（兩腳都要在系統裡） |
| `請款單` | ap_settlement | 出納匯款結清請款單 |
| `貸款繳款` / `貸款撥款` | loan | 走科目 2400，落籌資活動 |

🔴 **「轉存」的定義是「兩腳都在系統裡」。** 只有一腳配得上，代表對方帳戶不在
系統裡 —— 那它就不是轉存，是別的東西。

## 3. 2026-08 那一輪改了什麼

| 批次 | 筆數 | 從 → 到 | 依據 |
|---|---|---|---|
| 薪資代發 | 263 | 轉存 → 代收薪資／代發薪資 | 備註帶 `crm_staff` 人名，每個人**轉入 ≈ 轉出** |
| 薪資代發（補漏） | 8 | 同上 | 妍蓁（陳妍蓁）、依靜（林依靜）**不在 151 人名冊裡**，第一輪漏掉 |
| 代收代付 | 4 | 轉存 → 代收代付 | 備註寫「代付」（動工、木子映像） |
| 發票代開（匯出腳） | 1 | 轉存 → 發票代開 | 小公視 360,000：3/24 收同額代開款、3/26 全額匯出 |
| 發票代開（手續費匯入） | 54 | 轉存 → 發票代開 | 🔴 **48 筆金額剛好等於某張代開發票面額的 8%**（480=6,000×8%、1,176=14,700×8%…） |
| 現金代收 | 3 | 轉存 → 現金代收 | 備註寫「應收發票：現金收款／士源代收」，且發票不在系統 |
| 跨行手續費 | 37 | 支出拆出 `bank_fee` | 富邦轉出 35,015 vs 合庫收到 35,000，差額**全部都是 15** |

結果：全期間勾稽差額 **624,511 → 79,895**，2026-Q1 與 2026-04 **歸零**。

### 剩下的 79,895 不是錯帳

貸款專戶月轉的**在途資金**（月底轉出、下月初入帳）＋ 手續費。兩腳都在系統裡，
現金流量表本來就該告訴你「有多少還在路上」。

### 還沒認的（合計約 1.2 萬）

- 若若012200 兩筆（2024-04-02，＋10,000／＋4,700）—— 沒有匯出腳、備註無線索
- 「#中山分行」−13,274、「和上一比合併營業部」＋10,000

## 4. 三個會再犯的坑

🔴 **`bank_fee` 是外加在 `expense` 之上的，不是含在裡面。**
`cash_entry_flow = deposit − expense − bank_fee − claim`，列表的支出欄顯示
`expense + bank_fee`。所以認列匯費要用**「總流出不變」**當不變量：

```
total_out = expense + bank_fee
bank_fee  = fee
expense   = total_out − fee
```

只寫 `bank_fee` 不從 `expense` 扣，帳上會多流出一筆 —— 反而製造新的勾稽差額。
（v2.4.143 就是這樣寫錯，v2.4.144 修掉。當時的 e2e 只斷言 `bank_fee == 10`，
所以抓不到 —— **要釘不變量，不是釘單一欄位**。）

🔴 **`transfer` 的收支不進淨流，但**餘額**會動。** 任何「單腳的轉存」都是一筆
差額。設計新類別時先問：這筆錢有沒有真的離開／進入公司？有 → `passthrough`。

🔴 **非現金帳戶（股東往來）的收支不能算進現金流。** 期初／期末只取
`split_bank_lines(...)["cash"]`，迭代那側也必須一致，否則股東往來上每記一筆
就多一筆差額（v2.4.142 修）。

## 5. 匯入時的自動判斷

規則在**財務管理 › 收支明細 › 🔍 對帳系統 › 分類規則**。比對的是**整列文字**
（含對方戶名），由上而下、先命中的先贏；綁帳戶的規則贏過「所有帳戶」。

目前生產的規則（順序 20–26，**刻意排在既有「轉存」那幾條 90–120 之前**——
那正是這批資料當初被歸錯的原因）：

| 順序 | 關鍵字 | → 類別 | 方向 | 為什麼可以這樣判 |
|---|---|---|---|---|
| 20 | 薪水 | 代收薪資 | 不限 | 實測 105 筆**全在收入側** |
| 21 | 眷保 | 代收薪資 | 不限 | 57 筆全在收入側 |
| 22 | 薪資 | 代發薪資 | **只支出** | 🔴 薪資 10 收 / 79 支，**兩側都有** |
| 23 | 薪資 | 代收薪資 | **只存入** | 同上，另一半 |
| 24 | 發票 | 發票代開 | 不限 | 365 筆全在收入側 |
| 25 | 代付 | 代收代付 | 不限 | 4 筆全在收入側 |
| 26 | 代收 | 現金代收 | 不限 | 3 筆全在收入側 |

**方向條件**（`bank_import_rules.only_direction`，v2.4.145）是為了「薪資」這種
同一個關鍵字兩個方向是**不同類別**的情況。

🔴 它跟 `direction` 是兩件事，不要混：`direction` 是「餘額鏈推不出方向時的提示」，
`only_direction` 是**篩選條件**。方向不明時（第一列沒有前一列餘額也沒有總計）
帶方向條件的規則會被**跳過** —— 不知道方向就不要假裝知道。

🔴 **不限方向的規則排在前面會蓋掉方向規則**。「為什麼我的新規則沒生效」十次
有九次是這個。

## 6. 請款單的勾連

出納統一匯款、備註寫姓名。費用在**請款單建立那個月**就認列（權責制），匯出去
那筆收支是 `ap_settlement`、**不再認列一次** —— 所以不會重複計。

但 `payment_request_id` 是一對一，而實務上一個人的多張單常併成一筆匯出，掛不上去
（實測 322 筆 ap_settlement，硬連結**一筆都沒有**）。v2.4.143 起有
`crm_cash_payment_links`（多對一）＋ 手續費容差，在收支明細的支出列展開
「關聯請款單」。

owner 2026-08-22 決定：**歷史不回頭勾，九月起才勾**。這對現金流**零影響**
（那些匯款早就計入營運活動），只是 8 月以前沒有對帳軌跡。

🔴 付款側的容差方向跟收款側**相反**：收款是「分配比實收多 ≤ 容差 ＝ 對方代扣匯費」，
付款是「分配比實付少 ≤ 容差 ＝ 我們付了手續費」。共用同一支判讀會把手續費
判成「還有單沒掛」。

## 6.5 這幾條規則各自只有一份（2026-08-22 /simplify 五輪之後）

改任何一條之前先確認你改的是正本，不是複本：

| 規則 | 正本 | 兩側／多處呼叫 |
|---|---|---|
| 收付齊了沒（含匯費容差＋「一毛沒收不算收齊」） | `amount_is_settled` | 發票、請款單共用 |
| 分配判讀（empty/ok/fee/over/under） | `alloc_verdict(actual, allocated, side=)` | `side="receipt"` / `"payment"` |
| 認列匯費（不變量＝總流出不變） | `recognize_bank_fee` | 收支寫入路徑 |
| 什麼算現金帳戶 | `cash_account_ids` | `build_cashflow` 與現金流鑽取 |
| 內部移動（本金不列入活動） | `INTERNAL_MOVEMENT_TREATMENTS` | 三處判定 |
| 分配列驗證（四條寫入路徑） | `resolve_allocs(kind=)` | 收付兩側 |
| 分配寫入流程 | `_write_allocs(kind=)` | 兩支 PUT 端點 |
| 分配面板（前端） | `_ALLOC_SIDES` ＋ `_renderAllocs` | 關聯發票／關聯請款單 |

🔴 這些本來全是「兩份」。它們**在同一次 commit 裡就漂開過**：狀態列的
`msg` vs `message`、預帶面額 vs 尚欠、跨帳本一邊回 409 一邊回 422、
現金流鑽取比它鑽的那個數字多 777,000。
