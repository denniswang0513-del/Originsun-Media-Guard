# /polish

目標：把當前分支相對於主分支的變更整理到可合併狀態，且**不改壞範圍外的任何東西**。

## 核心原則

1. **範圍鎖死。** 只准修改 diff 內的檔案。範圍外看到問題一律只寫進報告。禁止跨檔案抽 helper、禁止改 import 路徑、禁止移動檔案。
2. **每階段：改 → 跑全套測試 → commit。** 只跑相關測試不夠，改 A 壞 B 的 B 通常在別的檔案。
3. **硬上限，不是跑到沒東西改。** 撞上限就停，把剩下的交給使用者。
4. **測試失敗不修測試。** 回退該階段並回報。
5. 每階段一個 commit，不 squash，方便 bisect。
6. **修 bug 前先過 `/assess`。** 階段一的每個 review 發現都要先有評估卡、先有紅測試，過閘門的才修；沒過的原樣進報告。

## 前置檢查（不通過就停止）

1. 主分支名稱：讀 CLAUDE.md 的 `polish.base`，沒有就用 `main`，再沒有用 `master`。
2. 有未 commit 變更 → 先 commit `polish: baseline`。
3. 測試指令優先順序：參數 `--test "<cmd>"` → CLAUDE.md 的 `polish.test` → 自動偵測（package.json scripts.test / pytest / cargo test / go test ./... / 其他）。找不到就問使用者，不要猜。
4. 跑一次全套測試建立基準。基準失敗 → 回報並停止，polish 不修既有失敗。
5. 範圍 = `git diff <base>...HEAD --name-only`。使用者給 `focus on <範圍>` 則進一步縮小。

## 階段零：安全網

- 對 diff 涉及的每個模組，檢查其公開函式有沒有測試。
- 沒有的補「特徵測試」：不判斷對錯，只把現在的行為釘住（給定輸入 → 斷言現在的輸出）。
- 只補 diff 有動到的函式，沒動到的舊程式碼不補。
- 跑全套測試 → 通過則 commit `polish: safety net`，失敗則回退並停止（代表特徵測試本身寫錯，回報）。

## 階段一：Code Review

- 執行 `/code-review`（**不加 --fix**），限定範圍，拿到發現清單。
- 對清單執行 `/assess --fix`：每項一張評估卡、同根因合併、依影響排序、逐張過閘門。
  通過的：紅測試 → 修 → 綠 → 全套測試 → **一張卡一個 commit** `polish: BUG-N <一句話>`（body 帶現象／根因／驗證）。
  沒通過的：報告「沒動的東西」一行一條（擋在哪條），完整卡放附錄，不問。
- 任一張卡全套測試失敗 → 回退那張卡的檔案、卡改判「回報」、繼續下一張（不再是整個流程停止；停止條件改成「連續 2 張回退」）。
- 本輪結束不再另外 commit `polish: review round N`；卡片 commit 就是這輪的紀錄。
- 停止條件：本輪無新發現，或剩餘項目全在 `.polish-ignore`。
- 上限 2 輪。第 2 輪仍有新發現 → 記錄「review 未收斂」，照樣進階段二。
- 使用者判定為誤報的項目寫入 `.polish-ignore`（每行 `檔案:規則:一句描述`）。

## 階段二：Simplify

- 執行 `/simplify`，只針對範圍內檔案。
- 額外約束：不新增抽象層（base class、trait、共用 helper），除非同一段邏輯在範圍內出現 3 次以上；不跨檔案搬程式碼。
- 跑全套測試。失敗 → 回退本階段，記錄，跳過進階段三，不重試。
- 通過 → commit `polish: simplify round N`。
- 停止條件：本輪變更少於 20 行。
- **硬上限 2 輪。** 第 2 輪仍超過 20 行 → 停，把 simplify 剩餘意見寫進報告。多輪 simplify 會震盪，超過 2 輪不代表更好。

## 階段三：AI 可維護性（只跑一輪）

**自動修（都在同檔案內、不改公開介面）：**
- 函式超過 50 行**且有多職責訊號**（分段註解如 `// step 1`、可命名的中間結果、多個獨立處理區塊）→ 同檔案內拆成小函式；沒有訊號就放著，不要為了行數而拆
- 巢狀超過 3 層 → 提早 return 或抽小函式
- 魔術數字、魔術字串 → 具名常數
- 公開函式缺 docstring → 補一行；語言支援型別標註則補上
- 公開函式無測試 → 補一個最小測試
- 「// 這裡是做 X」型註解 → 優先改名稱，名稱夠清楚就刪註解
- 新增全域可變狀態 → 改成參數傳入

**只回報不修（涉及跨檔案或風險較高）：**
- 函式超過 200 行 → 無條件回報（逼近工具單次讀取分段邊界，agent 可能只讀一半就改）
- 檔案超過 800 行回報、超過 1500 行強烈建議拆、超過 2000 行標紅（超過 Read 工具單次讀取上限，agent 無法一次看完整檔），附拆分建議
- 模組職責不清、需要重整邊界
- 循環依賴

**更新 CLAUDE.md：** 在 `## 模組職責` 段落補上這次新增或大改的模組各一行說明；在 `## 不要動的地方` 補上這次發現的地雷。沒有這兩個段落就建立。

跑全套測試 → 通過則 commit `polish: maintainability`，失敗則回退並記錄。

## 收尾

1. 再跑一次 `/code-review`（不加 --fix），只回報。有新發現不自動修，避免無限迴圈。
2. 全流程 commit 總數上限 6（階段一的卡片 commit 另計，上限 10），超過即停。
3. 輸出報告，格式固定：
polish 報告

範圍：<base>...HEAD，N 個檔案 基準測試：通過 階段零 safety net：補 X 個測試 階段一 review：N 輪，寫卡 X 張，修 Y 張，不動 Z 張，收斂 / 未收斂 階段二 simplify：N 輪，共改 X 行，收斂 / 撞上限 / 跳過 階段三 maintainability：自動修 X 項，回報 Y 項 收尾 review：無新發現 / 發現 X 項（未修） CLAUDE.md：更新了什麼 commits：<hash 與訊息> 停止原因：正常結束 / 撞上限 / 測試失敗於階段 N 需要人工決定：

## 參數

- `/polish` — 預設
- `/polish focus on <範圍>` — 縮小範圍
- `/polish --test "<cmd>"` — 指定測試指令
- `/polish --skip simplify` — 跳過階段二
- `/polish --dry` — 只回報，不改不 commit
- `/polish --debt` — 舊債模式：範圍改成整個專案，**只回報不修**，列出超長檔案（> 800 行，2000 行以上標紅）、超長函式（> 200 行）、無測試模組、巢狀過深函式、循環依賴，依嚴重度排序。使用者看了報告另開分支處理，一次一個模組。

## 不要做的事

- 不要因為「還有改進空間」而多跑一輪
- 不要 squash commits
- 不要動範圍外的檔案，即使只是「順手」
- 不要修測試讓它通過
- 不要跳過 /assess 直接修 review 發現，即使看起來很小
- 不要在 --dry 或 --debt 模式下做任何寫入
