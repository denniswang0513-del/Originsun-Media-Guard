# /assess

目標：在「發現 bug」和「改程式碼」之間插一道閘門。**沒有卡、沒有紅測試，不准修。**

**卡片是誰看的**：是你自己的。它的用途是逼自己把根因、影響、重現想清楚再動手，以及留下 commit 可追的證據。
**不是**送給使用者批准的表單——使用者不想審卡片，他要的是「仔細評估、不亂動」。所以：
過閘門 → 直接修，不問；沒過閘門 → 直接不動，不問。使用者只會在報告末尾看到一行一條「沒動的東西」，想追再點開附錄。

## 核心原則

1. **先全部寫卡、再排序、再修。** 不是看到一個修一個。5 個症狀常常是 1 個根因。
2. **紅→綠是硬規定。** 第 4 欄的測試要先看到失敗，才准動程式碼。沒看到紅就修 = 修一個不存在的 bug。
3. **不確定就不修。** 卡片任一欄寫「不確定」，判定自動變「不動」。猜對的修法跟猜錯的修法在 diff 上長得一樣。
4. **一張卡一個 commit。** commit body 帶精簡版（現象／根因／驗證三行），bisect 時看得懂。
5. **上限 20 張。** 超過的只列一行標題進報告，評估本身不能把額度吃光。
6. **全程不問。** 閘門的判定就是最終判定。唯一例外：使用者**指名**要修的 bug 被閘門擋下 → 用一句話說擋在哪條、問要不要照樣修。

## 評估卡（固定 7 欄）

```
### BUG-<序號>：<一句話>
1. 現象       檔案:行號；觸發條件；實際 vs 預期
2. 根因       指到具體一行／一個判斷，說「為什麼」不是「哪裡」。
              不確定 → 寫「不確定」，判定＝不動
3. 影響範圍   grep 呼叫端逐一列出；跨檔？跨前後端？NAS 容器／機隊 OTA 吃不吃到？
              碰到 public_router、ota_manifest、requirements_*、core/schemas、
              main.py／main_website.py 雙定義路由 → 標「高」
4. 重現       用什麼證明它壞：一支會失敗的測試（優先），或 ruff／eslint 的那一行輸出。
              寫不出重現 → 判定＝不動
5. 修法       至少兩個選項（其中一個可以是「不修」）；選哪個、為什麼；預估 diff 行數
6. 驗證與回退 改哪些檔；修完怎麼證明（第 4 欄轉綠 ＋ 全套綠）；失敗怎麼回退（git checkout 那些檔）
7. 判定       修 ／ 不動（附是哪條閘門）
```

**短卡**（機械性項目：ruff F401/F841、eslint gate 規則、唯一來源的漏 import）：只填 1、3、4、7。第 4 欄可以直接是 lint 輸出行，不用另寫測試；但修完要重跑 lint 看它消失 ＋ 全套測試。

## 閘門（任一條中就不修）

| 條件 | 判定 |
|---|---|
| 第 2 或第 4 欄是「不確定」 | 不動 |
| 影響範圍「高」 | 不動 |
| 修法要跨檔搬程式碼、改公開介面（函式簽名、API 回傳形狀、DB 欄位）、加抽象層 | 不動 |
| 撞到 CLAUDE.md `## 不要動的地方` 任一條 | 不動（卡上註明撞哪條） |
| 預估 diff > 40 行 | 不動 |
| 修法需要改測試才能綠 | 不動（既有測試釘的行為可能才是對的） |
| 同根因已有另一張卡 | 合併成一張，序號保留較小的，一次修 |

「不動」不是「等使用者決定」——是最終結果。它們以一行一條的形式出現在報告的「沒動的東西」清單（`BUG-N <一句話> — 擋在 <哪條>`），完整卡片放報告附錄。使用者不回應就是同意不動。

## 流程

```
1. 收集   把這次要處理的 bug 清單列出來（來源：/code-review 輸出、lint 輸出、使用者指名）
2. 寫卡   每個一張；同根因合併；超過 20 張的只列標題
3. 排序   影響範圍 高→中→低；同級依「呼叫端數量」
4. 逐張過閘門
   通過 → 寫第 4 欄的測試 → 跑它，必須紅 → 修 → 跑它，必須綠 → 全套測試 → commit
          全套失敗 → git checkout 第 6 欄列的檔 ＋ 刪剛加的測試 → 卡改判「不動」＋記失敗原因 → 下一張
   不通過 → 卡片原樣留著
5. 輸出   正文：修了 X 張（一行一條 ＋ commit hash）、沒動 Y 張（一行一條 ＋ 擋在哪條）
          附錄：所有完整卡片。正文要能在 20 行內看完。
```

**紅測試放哪**：跟被修模組同名的既有測試檔（`tests/unit/test_<模組>*.py`）；沒有就新開。掃原始碼的規則測試用 `_srcscan.flow_body`。

**commit 格式**：
```
<前綴>: BUG-<序號> <一句話>

現象：...
根因：...
驗證：<測試檔::測試名> 紅→綠；全套 N 支通過
```
前綴由呼叫端決定（`polish:`／`health:`／手動時 `fix:`）。

## 參數

- `/assess` — 對目前對話裡剛列出的 bug 清單寫卡，只評估不修
- `/assess <描述或檔案:行號>` — 單一 bug 寫一張完整卡
- `/assess --fix` — 寫卡 ＋ 過閘門的直接修（/health、/polish 用這個）
- `/assess --short` — 全部用短卡（lint 類）

## 不要做的事

- 不要沒看到紅就修
- 不要為了讓測試綠而改測試或加 `noqa`／`eslint-disable`
- 不要把兩張不同根因的卡塞進一個 commit
- 不要在第 5 欄只寫一個選項
- 不要因為「順手」修卡片範圍外的東西
- 使用者說「直接修」= 跳過卡片但**不跳過紅→綠**
- 不要把「不動」的卡包裝成問題丟給使用者；不動就是答案
- 不要在正文貼完整卡片；正文是清單，卡片是附錄
